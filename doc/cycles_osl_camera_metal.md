# Custom (OSL) cameras on Metal

Cycles has a custom camera type whose rays are generated by an OSL shader. Upstream it works on
the CPU and with OptiX, because those run the OSL runtime. Metal has no OSL back end, so a custom
camera rendered black there. This fork makes custom cameras work on Metal.

The motivation is the Lens Sim add-on, which simulates real lenses by generating an OSL camera
shader for the selected lens. Nothing of the add-on is part of this repository: the
implementation is a generic translator from compiled OSL bytecode to a Metal function, so every
OSL camera shader that stays within the supported language subset works, including Blender's own
camera templates in `scripts/templates_osl`.

## What a lens shader needs

These are the features the add-on's shaders use, which the Metal path therefore has to provide.
All of them are supported.

| Area | Features |
| --- | --- |
| Inputs | sensor position `P` with derivatives, lens random numbers `N` |
| Attributes | `cam:sensor_size`, `cam:image_resolution`, `cam:aperture_size`, `cam:aperture_position`, `cam:aperture_aspect_ratio`, `cam:focal_distance` |
| Outputs | `position`, `direction`, `throughput`; zero throughput discards the ray; ray differentials |
| Control flow | `if`, `for`, `while`, `do`, `break`, `continue`, inlined functions with early `return`, `exit()` |
| Data | `int`, `float`, vectors, colors, matrices, fixed-size arrays (lens tables of up to 200 entries), structures |
| Math | arithmetic with OSL's division-by-zero rule, comparisons, `pow`, `sqrt`, `exp`, `log`, trigonometry, `sincos`, `floor`, `round`, `min`, `max`, `mix`, `abs` |
| Geometry | `dot`, `cross`, `length`, `normalize`, `refract`, `rotate`, matrix construction, `transform`/`transformv` |
| Sampling | `hashnoise` with the same values as other devices, `wavelength_color` for chromatic aberration |
| Parameters | about 50 numeric shader parameters driven by the add-on (focus, f-stop, tilt-shift, bloom, distortion, ...), which change during playback and viewport editing |
| Robustness | array indices out of range are clamped, loops cannot hang the GPU |

## Design

```
camera shader (.osl)
   |  oslc, run by Blender's Python (unchanged)
   v
bytecode (.oso), stored in the camera datablock (unchanged)
   |  OSLManager::device_update_camera_metal()            scene/osl.cpp
   v
Metal source   <- metal_osl_camera_translate()             device/metal/osl_camera_translate.cpp
   |  MetalDeviceKernels::compile_camera_function()        device/metal/kernel.mm
   v
GPU binary of one function
   |  added to the finished pipeline of integrator_init_from_camera
   v
camera_sample_custom() calls it through a visible function table   kernel/camera/camera.h
```

**Translator.** `osl_camera_translate.cpp` parses the bytecode (symbols and instructions with
structured jump targets) and emits one Metal function. Loops become `for (;;)`, an inlined
function body becomes `do { } while (false)` so that `return` is `break`, and a return from inside
a loop sets a flag that is checked after the loop. The translator depends only on the C++
standard library, so it also builds as a standalone tool for testing.

**Ray differentials.** The OSL runtime differentiates the shader automatically to get the ray
differentials. The translation does the same with dual numbers (`OslDual<float>` and
`OslDual<float3>` in `osl_camera_prelude.h`). Two data flow passes find the symbols that both
depend on the sensor position and reach an output that needs derivatives; only those are dual,
everything else is plain floats. A shader that outputs `dPdx`, `dPdy`, `dDdx` or `dDdy` itself
gets no automatic differentiation, as on other devices.

**Tables.** Lens shaders keep their data in local arrays. An array that is only a copy of a
constant array reads the constant directly, and an array that is filled element by element with
constants (how the OSL compiler initializes an array of colors, such as a 128x128 aperture image)
becomes a constant array. Nothing is copied or assigned per ray.

**Parameters.** Numeric parameters that the camera assigns are not baked into the function. They
are read from the new `camera_script_params` kernel array, so changing a parameter only uploads a
few words: no translation, no compilation. Strings are constants of the translation. The
translation is redone only when the bytecode, the set of assigned parameters, a string value or
the scene's color space changes.

**Kernel hook.** `MetalAncillaries` has one more slot, `vft_osl_camera`, directly after the
textures so that its position does not depend on the library variant. Only
`integrator_init_from_camera` calls it, and only for custom cameras. Its pipeline is created with
`supportAddingBinaryFunctions`, and the camera function of the scene is added with
`newComputePipelineStateWithAdditionalBinaryFunctions`, which links a finished binary without
recompiling the kernel. The precompiled kernel libraries therefore stay independent of the scene.
Switching lenses costs about 0.4 s for a new lens and nothing for one used before in the session.

**Kernel data.** The function reads camera attributes and matrices directly from the kernel
parameter buffer. The device passes the offsets as `OSL_KD_*` defines when it compiles the
function.

**Math mode.** The camera function is compiled with relaxed math
(`MTLMathModeRelaxed`): operations may be reordered, but infinities and NaN keep their meaning.
It is about 30% faster than safe math on the most complex lens and equally close to the CPU.
`CYCLES_METAL_OSL_CAMERA_MATH_MODE=0` selects safe math and `2` fast math.

**Failure handling.** A shader that uses something unsupported renders black on Metal, as a
shader that fails to compile does on other devices, and Blender shows a warning naming the
instruction. The render session stays usable, so the shader can be edited and rendered again. A
custom camera without a shader renders black on all devices. `CYCLES_METAL_OSL_CAMERA=0` disables
the feature.

**Other devices** are unaffected: `Device::set_osl_camera_source()` does nothing by default. With
GPU and CPU rendering together, the CPU runs the OSL runtime and Metal the translation.

## Supported OSL

Supported: all of the table above, plus `Dx`, `Dy`, `filterwidth`, `area`, `calculatenormal`,
hyperbolic functions, `erf`, `erfc`, `cbrt`, `logb`, `fmod`, `step`, `smoothstep`, `select`,
`sign`, `isnan`, `isinf`, `isfinite`, integer and bit operations, `hash` of numbers, matrix
arithmetic, `determinant`, `transpose`, named spaces (`common`, `world`, `camera`, `screen`,
`raster`, `NDC`), `getmatrix`, color spaces (`rgb`, `hsv`, `hsl`, `YIQ`, `XYZ`, `xyY`, `sRGB`),
`luminance`, `blackbody`, `cellnoise`, Perlin `noise`/`snoise` in 1 to 4 dimensions with
derivatives, `raytype`, `scene:time`, `scene:frame`, and string comparisons on constant strings.

Not supported, reported with a warning: closures, textures and point clouds, `trace`, messages,
splines, Gabor, simplex and periodic noise, `hash` of strings, and strings computed at render
time.

## Matching the CPU

The results are meant to equal the OSL runtime, including where it deviates from what one might
expect:

* Division by zero is zero, `sqrt` and `log` of invalid arguments are defined, `pow` of a negative
  base is real only for integer exponents.
* `min` and `max` of equal values return the second argument, which matters for derivatives.
* The derivative of `atan2` has the sign convention of OSL's `dual.h`.
* Attribute conversions follow `kernel/osl/services_shared.h`: a float fills all components of a
  vector, a pair of floats is padded with zero or averaged.
* The XYZ to RGB matrix is derived from the chromaticities of the scene color space as the OSL
  runtime does.

Images are not bit-identical. Where a shader feeds a value into `hashnoise`, the last bit of that
value can differ between devices, which gives another random number. The add-on uses this for
chromatic aberration, bloom and halation: those renders have the same expected image but another
noise pattern, and converge to the same result.

## Tests

`tests/python/cycles_osl_camera_scenes.py` renders on `CPU`, `METAL` or `METAL_CPU`, and
`tests/python/cycles_osl_camera_compare.py` compares two output directories.

```
blender -b --factory-startup --python tests/python/cycles_osl_camera_scenes.py -- --output out/cpu --device CPU
blender -b --factory-startup --python tests/python/cycles_osl_camera_scenes.py -- --output out/metal --device METAL
blender -b --factory-startup --python tests/python/cycles_osl_camera_compare.py -- out/cpu out/metal
```

* 50 probe scenes evaluate groups of OSL operations and their derivatives per pixel and write the
  values as the throughput of a camera looking at a white world, with one sample per pixel. Both
  devices must agree to floating point accuracy.
* 2 scenes repeat a probe with other parameter values.
* 12 render scenes: explicit derivatives, Blender's `basic_camera.osl`, `advanced_camera.osl`
  (distortion, swirl with Perlin noise, depth of field) and `cubemap_camera.osl`, and a shader
  written for the test that traces rays through a Cooke triplet with arrays, loops, early exits,
  dispersion, motion blur, adaptive sampling and extra passes.
* `--session` renders a sequence of edits in one persistent render session: parameter changes,
  another shader, an unsupported shader, a regular camera, no shader, an animated parameter.
* `intern/cycles/test/device_metal_osl_camera_test.cpp` tests the translator without a GPU.

## Results

Apple M5, 10 GPU cores, 16 GB, macOS 27. All comparisons are CPU against Metal in the same build.

| Test | Result |
| --- | --- |
| Probe scenes | 52 of 52 match without a single outlier pixel; 17 are bit-identical, the median largest difference is 2e-6 |
| Render scenes | 12 of 12 match |
| Session, Metal | 11 of 11 steps match |
| Scenes and session, GPU + CPU | 64 of 64 and 11 of 11 match |
| Lens Sim, all 84 bundled lenses | all translate, compile and match; largest difference of the image mean 0.1% |
| Lens Sim, 21 configurations | all match: fisheye, anamorphic, zoom, aspheric, macro, the simplified lens, chromatic aberration (3 kinds), halation, bloom and glare, tilt-shift, distortion, swirl, radial blur, anamorphic emulation, aperture blades, exposure, flip |
| Lens Sim, one session | 8 of 8 steps match: lens switches, f-stop and focus edits |

The noisy configurations were also rendered with 4096 samples: the per-pixel difference fell by
the expected factor of 5.7 compared to 128 samples, with equal means.

Render time with the add-on's most complex lens (18-200mm zoom, 768x512, 1024 samples):

| Device | Time |
| --- | --- |
| CPU | 165.1 s |
| Metal, safe math | 15.8 s |
| Metal, relaxed math (default) | 11.1 s |

## Found on the way

* `matrix("camera", "world")` and `getmatrix("camera", "world", m)` in a camera shader crash the
  OSL runtime of the CPU device while it folds constants (also before this change). Metal renders
  them. The tests avoid them because there is no reference.
* The Metal kernel does not compile with `CYCLES_METAL_VISIBLE_SHADING=0` (also before this
  change), so custom cameras could not be tested with runtime-compiled generic kernels.

# Custom (OSL) cameras on Metal

Cycles has a custom camera type whose rays are generated by an OSL shader. Upstream it works on
the CPU and with OptiX, because those run the OSL runtime. Metal has no OSL back end, so a custom
camera rendered black there. This fork makes custom cameras work on Metal.

The first motivation was the Lens Sim add-on, which simulates real lenses by generating an OSL
camera shader for the selected lens. Nothing of the add-on is part of this repository: the
implementation is a generic translator from compiled OSL bytecode to a Metal function. After the
add-on worked, the translator was extended to the whole OSL language, so that any camera shader
that renders on the CPU renders on Metal.

## Design

```
camera shader (.osl)
   |  oslc, run by Blender's Python (unchanged)
   v
bytecode (.oso), stored in the camera datablock (unchanged)
   |  OSLManager::device_update_camera_metal()            scene/osl.cpp
   v
Metal source   <- metal_osl_camera_translate()             device/metal/osl_camera_translate.cpp
   |  MetalDeviceKernels::compile_camera_function()        device/metal/kernel.mm
   v
GPU binary of one function
   |  added to the finished pipeline of integrator_init_from_camera
   v
camera_sample_custom() calls it through a visible function table   kernel/camera/camera.h
```

**Translator.** `osl_camera_translate.cpp` parses the bytecode (symbols and instructions with
structured jump targets) and emits one Metal function. Loops become `for (;;)`, an inlined
function body becomes `do { } while (false)` so that `return` is `break`, and a return from inside
a loop sets a flag that is checked after the loop. Jump targets are validated before anything
else, so malformed bytecode is an error message and never a crash. The translator depends only on
the C++ standard library, so it also builds as a standalone tool for testing.

**Ray differentials.** The OSL runtime differentiates the shader automatically to get the ray
differentials. The translation does the same with dual numbers (`OslDual<float>` and
`OslDual<float3>` in `osl_camera_prelude.h`). Two data flow passes find the symbols that both
depend on the sensor position and reach something that needs derivatives; only those are dual,
everything else is plain floats. Besides the ray, derivatives are needed by `Dx()` and its
relatives, by image lookups (the resolution to use) and by Gabor noise (its filter). A shader
that outputs `dPdx`, `dPdy`, `dDdx` or `dDdy` itself gets no automatic differentiation of the
ray, as on other devices.

**Tables.** Lens shaders keep their data in local arrays. An array that is only a copy of a
constant array reads the constant directly, and an array that is filled element by element with
constants (how the OSL compiler initializes an array of colors, such as a 128x128 aperture image)
becomes a constant array. Nothing is copied or assigned per ray.

**Parameters.** Numeric parameters that the camera assigns, including vectors and matrices, are
not baked into the function. They are read from the `camera_script_params` kernel array, so
changing a parameter only uploads a few words: no translation, no compilation. Strings are
constants of the translation. The translation is redone only when the bytecode, the set of
assigned parameters, a string value or the scene's color space changes.

**Strings.** A GPU has no strings, and the shader needs none at render time: a string is the
index of its text in a table that only exists while translating. An analysis finds the set of
values each string symbol can have. With one value the string is a constant. With a few values
(a name chosen by a condition, an element of an array of names, the argument of a function called
with different names) every instruction that needs the text, such as `noise(name, ...)`,
`transform(space, ...)`, `strlen()` or `texture(file, ...)`, is emitted once for each value and
selected by the index. Comparing and assigning strings only needs the indices. Text functions
(`concat`, `format`, `substr`, `split`, `regex_search`, `stoi`, `hash`, ...) are evaluated by the
translator. The one thing that cannot be translated is a string made from a number at render
time (`format("%d", i)`) that the shader then looks at; printing it is fine.

**Images.** `texture()`, `texture3d()`, `environment()` and `gettextureinfo()` use the images of
Cycles, like the OSL runtime of the other devices: the file is loaded by the image manager with
default settings, and the lookup is the kernel's image code, with the texture cache, tiles and
mip levels chosen from the derivatives of the coordinates. The camera function is compiled on
its own and has no access to that code, so it does not sample images itself. It returns a request
(image, coordinates, color for a missing image) instead of a ray, the kernel answers it in
`camera_custom_image_request()` and calls the function again with the result appended to its
input. A shader without lookups pays nothing for this, and a ray with N lookups runs the function
N + 1 times, up to 32 lookups for one ray. If the texture cache has not loaded the tile yet, the
kernel generates the ray again later, like for image textures of materials. The kernel ID of
each image is a word of the parameter array, so the function does not depend on the scene.

**Dictionaries.** `dict_find()`, `dict_next()` and `dict_value()` query XML with XPath. The host
evaluates the queries during the translation with the same library as the OSL runtime; the
shader handles node numbers and reads values from tables.

**Messages** (`setmessage`, `getmessage`) are variables of the function, with the rule that a
message keeps the type and value of the first time it is set. **Closures** have no meaning for
a camera: they are not computed.

**Runtime library.** `osl_camera_prelude.h` implements the OSL operations in Metal. Its parts
for Perlin, periodic, simplex and Gabor noise, splines and color conversions with derivatives
are only included when the shader uses them, which keeps the compilation of lens shaders short.
The hash functions, noise functions and their constants are the ones of Open Shading Language
and OpenImageIO (BSD-3-Clause), so that noise has the same values as on other devices. Gabor
noise additionally reproduces the random number sequence, the approximations of `exp2` and
`sincos` and the handling of singular filter matrices of the OSL runtime.

**Kernel hook.** `MetalAncillaries` has one more slot, `vft_osl_camera`, directly after the
textures so that its position does not depend on the library variant. Only
`integrator_init_from_camera` calls it, and only for custom cameras. Its pipeline is created with
`supportAddingBinaryFunctions`, and the camera function of the scene is added with
`newComputePipelineStateWithAdditionalBinaryFunctions`, which links a finished binary without
recompiling the kernel. The precompiled kernel libraries therefore stay independent of the scene.

**Kernel data.** The function reads camera attributes and matrices directly from the kernel
parameter buffer. The device passes the offsets as `OSL_KD_*` defines when it compiles the
function.

**Math mode.** The camera function is compiled with relaxed math
(`MTLMathModeRelaxed`): operations may be reordered, but infinities and NaN keep their meaning.
`CYCLES_METAL_OSL_CAMERA_MATH_MODE=0` selects safe math and `2` fast math.

**Failure handling.** A shader that cannot be translated renders black on Metal, as a shader
that fails to compile does on other devices, and Blender shows a warning naming the cause. The
render session stays usable, so the shader can be edited and rendered again. A custom camera
without a shader renders black on all devices. `CYCLES_METAL_OSL_CAMERA=0` disables the feature.

**Other devices** are unaffected: `Device::set_osl_camera_source()` does nothing by default. With
GPU and CPU rendering together, the CPU runs the OSL runtime and Metal the translation.

## Supported OSL

Everything that the OSL compiler can emit for a shader is handled. The source language itself
(functions, overloads, structures, operators, the preprocessor) is resolved by the compiler, so
the list is by what remains in the bytecode.

| Area | Features |
| --- | --- |
| Control flow | `if`, `for`, `while`, `do`, `break`, `continue`, inlined functions with early `return` from any depth, `exit()`, function calls in loop conditions |
| Types | `int`, `float`, `point`, `vector`, `normal`, `color`, `matrix`, `string`, structures, arrays of all of these including matrices and strings, arrays without a declared length, `closure color` (ignored) |
| Parameters | numbers, vectors, colors, matrices and strings assigned by the camera; defaults computed from other parameters; array and structure defaults; output parameters of any type |
| Globals | `P` (sensor position, with derivatives), `N` (lens sample); the others are zero as on other devices |
| Arithmetic | all operators on all types, with OSL's rules: division and modulo by zero are zero, conversions of numbers that do not fit saturate |
| Math | `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2`, `sinh`, `cosh`, `tanh`, `sincos`, `pow`, `exp`, `exp2`, `expm1`, `log`, `log2`, `log10`, `logb`, `sqrt`, `inversesqrt`, `cbrt`, `hypot`, `abs`, `sign`, `floor`, `ceil`, `round`, `trunc`, `fmod`, `mod`, `min`, `max`, `clamp`, `mix`, `select`, `step`, `smoothstep`, `linearstep`, `erf`, `erfc`, `isnan`, `isinf`, `isfinite`, `degrees`, `radians`, bit operations |
| Geometry | `dot`, `cross`, `length`, `distance`, `normalize`, `faceforward`, `reflect`, `refract`, `fresnel`, `rotate`, component access, `transform` of points, vectors and normals, matrix construction and arithmetic, `determinant`, `transpose`, named spaces (`common`, `world`, `camera`, `screen`, `raster`, `NDC`, `object`, `shader`), also chosen at render time |
| Derivatives | `Dx`, `Dy`, `Dz`, `filterwidth`, `area`, `calculatenormal`, through every differentiable function including noise, splines and color conversions |
| Color | `luminance`, `blackbody`, `wavelength_color`, `transformc` and `color(space, ...)` for `rgb`, `hsv`, `hsl`, `YIQ`, `XYZ`, `xyY`, `sRGB` and the scene's color space |
| Noise | `noise`, `snoise`, `pnoise`, `psnoise`, `cellnoise`, `hashnoise` and the generic `noise(name, ...)` / `pnoise(name, ...)` with `perlin`, `uperlin`, `cell`, `hash`, `simplex`, `usimplex`, `gabor` (with `anisotropic`, `direction`, `bandwidth`, `impulses`, `do_filter`), `null`, `unull`; 1 to 4 dimensions, float and vector results, periodic variants, derivatives |
| Splines | `spline` and `splineinverse` with `catmull-rom`, `bezier`, `bspline`, `hermite`, `linear`, `constant`, float and color knots, knot counts, derivatives by the position and the knots |
| Strings | comparison, assignment, arrays, `concat`, `format`, `substr`, `strlen`, `startswith`, `endswith`, `getchar`, `stoi`, `stof`, `hash`, `split`, `regex_search`, `regex_match`; `printf`, `fprintf`, `warning`, `error` print nothing |
| Images | `texture` (with `alpha`, `missingcolor`, `missingalpha`, explicit derivatives), `texture3d`, `environment`, `gettextureinfo` (`resolution`, `channels`, `exists`, `averagecolor`) |
| Scene | `getattribute` of `cam:sensor_size`, `cam:image_resolution`, `cam:aperture_size`, `cam:aperture_position`, `cam:aperture_aspect_ratio`, `cam:focal_distance`, `scene:time`, `scene:frame` into every type the other devices accept; `getmatrix`, `raytype`, `isconnected`, `isconstant`, `backfacing`, `surfacearea`, `arraylength` |
| Other | `setmessage`, `getmessage`, `dict_find`, `dict_next`, `dict_value`, `hash` of numbers |

What a camera shader cannot do on any device behaves the same on Metal: `trace()` finds nothing
and `pointcloud_search`, `pointcloud_get` and `pointcloud_write` return zero, because Cycles has
no point clouds and gives camera shaders no scene to trace.

Limits of the translation:

* A string that is made from a number at render time and then compared, measured or used as a
  name cannot be translated. The shader renders black with a warning.
* At most 32 image lookups for one ray. A ray with more is not generated.
* A loop ends after a million iterations, so that a shader that never terminates cannot hang
  the GPU.
* Strings can have 256 values, and one instruction is emitted for at most 512 combinations of
  the values of its strings.

## Matching the CPU

The results are meant to equal the OSL runtime, including where it deviates from what one might
expect:

* Division by zero is zero, `sqrt` and `log` of invalid arguments are defined, `pow` of a negative
  base is real only for integer exponents.
* `min` and `max` of equal values return the second argument, which matters for derivatives.
* The derivative of `atan2` has the sign convention of OSL's `dual.h`.
* `split()` makes at most `maxsplit` pieces, the last being the rest of the string.
* `matrix(space, ...)` applies the space first.
* A message that was queried before it exists can still be set.
* Colors given in a color space, `color("hsv", ...)`, have no derivatives; `transformc()` has.
* `splineinverse()` of a value outside of the spline returns the end of the last segment.
* An unknown spline basis is linear.
* `isconnected()` is 2 for the outputs that make the ray.
* A constant noise name can be `perlin`, `uperlin`, `cell`, `hash`, `simplex`, `usimplex`,
  `gabor` and the instruction names. `simplexnoise`, `usimplexnoise`, `null` and `unull` are only
  known when the name is chosen at render time, and as constants fail to compile.
* Attribute conversions follow `kernel/osl/services_shared.h`: a float fills all components of a
  vector, a pair of floats is padded with zero or averaged.
* The XYZ to RGB matrix is derived from the chromaticities of the scene color space as the OSL
  runtime does.

Images are not bit-identical. Where a shader feeds a value into `hashnoise`, the last bit of that
value can differ between devices, which gives another random number. The add-on uses this for
chromatic aberration, bloom and halation: those renders have the same expected image but another
noise pattern, and converge to the same result. Graphics hardware interpolates images with a few
bits of precision, so image lookups between pixel centers differ in the third decimal.

Metal does more than the CPU in a few places, where the OSL runtime has no way or fails:

* `gettextureinfo()`, `matrix("camera", "world")` and `getmatrix()` with constant arguments crash
  the OSL runtime of the CPU device while it folds constants for a camera shader (also before
  this change).
* An image whose file name is chosen at render time is looked up; the OSL runtime needs a
  constant name.

## Tests

`tests/python/cycles_osl_camera_scenes.py` renders on `CPU`, `METAL` or `METAL_CPU`, and
`tests/python/cycles_osl_camera_compare.py` compares two output directories.

```
blender -b --factory-startup --python tests/python/cycles_osl_camera_scenes.py -- --output out/cpu --device CPU
blender -b --factory-startup --python tests/python/cycles_osl_camera_scenes.py -- --output out/metal --device METAL
blender -b --factory-startup --python tests/python/cycles_osl_camera_compare.py -- out/cpu out/metal
```

* 109 probe scenes evaluate groups of OSL operations and their derivatives per pixel and write the
  values as the throughput of a camera looking at a white world, with one sample per pixel. Both
  devices must agree to floating point accuracy. `probe_*` covers what lens shaders use, `probe2_*`
  the rest of the language (splines, all kinds of noise, strings, messages, closures, arrays of
  every type, dictionaries, conversions), `probe_texture_*` the image lookups.
* 2 probe scenes for `gettextureinfo()` have no CPU reference and check the values that the
  shader must compute.
* 14 render scenes: explicit derivatives, Blender's `basic_camera.osl`, `advanced_camera.osl`
  (distortion, swirl with Perlin noise, depth of field) and `cubemap_camera.osl`, a shader written
  for the test that traces rays through a Cooke triplet with arrays, loops, early exits,
  dispersion, motion blur, adaptive sampling and extra passes, and a camera that reads a
  distortion map and an aperture image, also with the texture cache.
* `--session` renders a sequence of edits in one persistent render session: parameter changes,
  another shader, a shader that cannot be translated, a regular camera, no shader, an animated
  parameter.
* `intern/cycles/test/device_metal_osl_camera_test.cpp` tests the translator without a GPU.

## Results

Apple M5, 10 GPU cores, 16 GB, macOS 27. All comparisons are CPU against Metal in the same build.

| Test | Result |
| --- | --- |
| Probe scenes | 109 of 109 match without a single outlier pixel beyond the tolerance; apart from image lookups the differences are around 1e-6 |
| Render scenes | 14 of 14 match |
| Scenes, GPU + CPU | 123 of 123 match |
| Session, Metal and GPU + CPU | 11 of 11 steps match |
| Translator unit tests | 9 of 9 pass |
| Lens Sim, all 84 bundled lenses | all translate, compile and match |
| Lens Sim, 14 parameter sets on 2 lenses | 28 of 28 match: halation, chromatic aberration, tilt-shift, bloom and glare, distortion, swirl, radial blur, anamorphic emulation, flip, exposure, f-stop and focus overrides, sensor size, dolly zoom, sensor motion blur |

Render time before and after the extension to the whole language, Metal, 768x512, 512 samples,
best of several runs with the two builds alternating. The generated code of a lens shader is the
same as before; what changed is the kernel around it, which now can answer image lookups.

| Scene | Before | After | Change |
| --- | --- | --- | --- |
| Perspective camera with depth of field | 5.07 s | 5.09 s | +0.4% |
| Panorama camera | 3.15 s | 3.16 s | +0.4% |
| Custom camera, lens stack shader of the tests | 3.30 s | 3.30 s | -0.1% |
| Lens Sim 18-200mm zoom | 7.64 s | 7.68 s | +0.5% |
| Lens Sim 10mm fisheye | 4.60 s | 4.64 s | +0.8% |
| Lens Sim 100mm Petzval | 4.82 s | 4.88 s | +1.1% |
| Lens Sim, switching through all 84 lenses, 16 samples each | 21.9 s | 21.7 s | -0.7% |

Runs of one build differ by about 0.3%. Switching lenses includes translating and compiling each
shader, which got slightly faster because the Perlin noise code is no longer compiled for shaders
that do not use it.

## Found on the way

* `trace()` and `getmessage("trace", ...)` in a camera shader dereference a null pointer in the
  render services of the CPU device, and `gettextureinfo()`, `matrix("camera", "world")` and
  `getmatrix()` crash the OSL runtime while it folds constants (all also before this change).
  The tests avoid them on the CPU.
* The OSL runtime cannot load bytecode that contains an infinite or NaN constant, which the
  compiler writes when it folds an expression like `1e30 * 1e30`.
* The Metal kernel does not compile with `CYCLES_METAL_VISIBLE_SHADING=0` (also before this
  change), so custom cameras could not be tested with runtime-compiled generic kernels.
